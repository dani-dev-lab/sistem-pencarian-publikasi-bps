# OCR dengan GPU NVIDIA (18 Nov 2026)

Tujuan: mempercepat sisa OCR cache Kecamatan Dalam Angka (26 publikasi,
2.412 halaman tanpa lapisan teks; 973 sudah di-OCR dengan CPU, sisa 1.439)
dengan GPU laptop, tanpa mengubah perilaku bawaan (CPU) dan tanpa menyentuh
venv proyek. Bahan: folder `ocr-gpu-20261118/`.

## Pemasangan

- Perangkat: NVIDIA GeForce RTX 3060 Laptop GPU (6 GB), driver 621.24,
  mendukung CUDA sampai 13.5.
- Wheel torch CUDA yang tersedia untuk Python 3.14 + torch 2.15.0 hanya
  `cu132`. Torchvision `0.29.2` (versi venv CPU) tidak ada untuk cu132, jadi
  dipakai `0.29.1+cu132`.
- Venv terpisah `C:\Users\Dani\alat-ocr\venv-gpu`: torch 2.15.0+cu132,
  torchvision 0.29.1+cu132, easyocr 1.7.2, ditambah `requirements.txt`
  (skrip mengimpor paket `app`, jadi butuh Flask dan lainnya).
- Paket lain dikunci SAMA dengan venv proyek lewat
  `constraints-venv-gpu.txt` (`pip freeze` venv proyek tanpa torch dan
  torchvision). Hasil: `pip freeze` kedua venv hanya beda di torch dan
  torchvision, ditambah 3 paket di venv proyek yang tidak dipakai OCR
  (mysql-connector-python, ruff, Sastrawi).

## Perubahan kode (commit `c2088ab`)

- `app/services/ocr.py`: `GPU = False` di tingkat modul, dipakai
  `easyocr.Reader(gpu=GPU)`. Halaman yang di-OCR dengan GPU membawa
  `"perangkat": "cuda"` di berkas cache; bentuk cache CPU tidak berubah.
- `scripts/isi_cache_ocr.py --gpu`: menyalakan `ocr.GPU`. Skrip berhenti
  kalau `torch.cuda.is_available()` palsu, karena EasyOCR diam-diam pindah
  ke CPU. Diuji di venv proyek (torch CPU): pesan muncul, kunci dilepas.
- `perbarui.py` dan pipeline tidak tersentuh, jadi tetap CPU.

CPU yang dijalankan ulang identik dengan cache, jadi OCR CPU deterministik
dan keenam perbedaan berasal dari perangkatnya. Keenamnya hanya tanda baca
atau satu huruf, **tidak ada angka**:

| Cache CPU | GPU |
|---|---|
| `Indonesia:` | `Indonesia.` |
| `... Kecamatan Limpasu:` | `... Kecamatan Limpasu.` |
| `disampaikan   penghargaan` | `disampaikan  penghargaan` |
| `perbaikan publikasi ini; ...` | `perbaikan publikasi ini, ...` |
| `... Source of Villages/Subdistricts's` | `... Source of VillageslSubdistricts's` |
| `tengaln` | `tengan` |

Tidak ada yang jelas lebih baik: GPU salah di `/`→`l`, keduanya salah di
`tengah`.

### Penyebab beda: int8 (CPU) vs float (GPU)

Di CPU, EasyOCR 1.7.2 bawaannya (`quantize=True`) mengompres model
**pengenal** huruf ke bilangan bulat 8-bit (kuantisasi dinamis torch; tanda
di keluaran: peringatan `torch.quantize_per_tensor`). Kuantisasi dinamis
torch hanya berjalan di CPU, jadi di GPU model pengenal memakai float penuh.
Pembulatan yang sedikit beda mengubah pilihan karakter yang hampir seri,
dan itu tampak di tanda baca yang mirip bentuknya (`:`/`.`, `;`/`,`,
`/`/`l`).

Model **deteksi** (CRAFT, letak kotak kata) tidak dikuantisasi di kedua
perangkat, sehingga kotaknya identik sampai 0,00 pt. Itu yang terpenting
untuk parser koordinat: tata letak baris dan kolom yang dibacanya sama.

Run sungguhan dengan `--gpu` (log `data/log_ocr/20261118-090853.log`,

publikasi yang sama, Pandawan 2026 (8f34c2e7): 31 halaman CPU median
15,6 detik; 73 halaman GPU median 2,2 detik (wall 181 detik, ±2,5 detik
per halaman termasuk render). Sisa 1.439 halaman diperkirakan ±1 jam
dengan GPU, dibanding ±6,5 jam dengan CPU.

## Akibat bagi cache

Cache kecamatan kini campuran: 973 halaman CPU (int8) dan sisanya GPU
(float), termasuk di dalam satu publikasi (Pandawan 2026: hal. 1-31 CPU,
32-104 GPU). Halaman GPU bisa dikenali dari `"perangkat": "cuda"`. Mutu
OCR kecamatan tetap harus dinilai lewat sampel manual sesudah pemuatan,
seperti biasa; uji ini hanya menunjukkan bahwa perangkat tidak menjadi
sumber perbedaan yang berarti.
